# Диагностика фоновых уведомлений Android — 25.10.2026

Источник: предоставленный пользователем `logs.zip`, 30 файлов (10 сессий
24.10.2026), и текущее рабочее дерево Android. По журналу устройство Xiaomi,
API 36. Исходники приложения не изменялись, APK не собирался.

## Главная подтверждённая проблема

Telegram отклоняет `account.registerDevice` с `400 APP_PUSH_APIKEY_MISSING`.
Ошибка присутствует во всех 10 основных журналах, всего 20 записей. Отдельно
в MTProto-журналах найдено 13 запросов `registerDevice`: каждый следующий
ответ — `TL_error` с той же ошибкой. Это два представления событий, складывать
20 и 13 как независимые ошибки нельзя.

Примеры (номера строк внутри архива):

- `24_10_2026_15_19_57.txt:571` — отказ регистрации.
- `24_10_2026_20_17_40.txt:79` — 20:17:41.120, отказ регистрации.
- `24_10_2026_20_17_40.txt:459` — 20:17:44.038, повторный отказ.
- `24_10_2026_21_10_21.txt:75` и `:435` — ошибка сохраняется в последней сессии.

Токен Firebase получен; ошибки получения токена не найдены. Во всём архиве
нет записей `FCM received data`, `PRE START PROCESSING` или `isFcm=true`.
Есть 111 вызовов `processNewMessages` с `isFcm=false`: сообщения обрабатываются
по обычному соединению, а не через Firebase push. Отсутствие записей само по
себе не доказывает потерю конкретного сообщения; отказ регистрации — прямое
подтверждение неисправного push-канала в этих сессиях.

В текущих исходниках используется Telegram APP_ID 25495065 (`BuildVars.java`),
Firebase-проект `bygram-cf154`, sender/project number 993221992235
(`TMessagesProj_App/google-services.json`). Требуется проверить и настроить
push credentials для соответствующего Telegram API-приложения, согласованные
с Firebase-проектом. Клиентский `google-services.json` не заменяет настройку
отправителя на стороне Telegram. Конкретный доступный способ настройки нужно
проверить в аккаунте владельца API-приложения; доступа к нему в этой проверке нет.

Документация Telegram требует указать ключ приложения для отправки push:
https://core.telegram.org/api/push-updates .

## Дополнительный наблюдаемый сбой сети

В `24_10_2026_20_17_40.txt` приложение переходит в фон в 20:19:00.612.
В соответствующем `_net.txt:2082` и далее с 20:21:51.084 повторяются
разрывы соединения с reason 2 и таймауты; с 20:22:00 в основном журнале
возникают `UnknownHostException` для `dns.google.com` и
`mozilla.cloudflare-dns.com`. При недоступном push потеря обычного соединения
оставляет приложение без работающего канала получения новых сообщений.

Архив не позволяет отличить ограничение фоновой сети системой, проблему
маршрутизации/VPN/провайдера и временное отсутствие интернета. Причастность
энергосбережения Xiaomi не доказана; полного системного logcat/dumpsys нет.

## Дополнительные дефекты текущего кода

1. `PushListenerController.java:47` создаёт один статический `CountDownLatch`
   на весь процесс. `processRemoteMessage` ставит работу в UI/stage/notification
   очереди и ждёт этот объект на строке 1541. После первого `countDown` все
   следующие ожидания завершаются немедленно. Поэтому Firebase callback может
   закончиться до обработки уведомления. Извлечение фактической декларации в
   JVM-проверку подтвердило это поведение. Это риск после восстановления push,
   но архив не подтверждает его срабатывание: входящих FCM в нём нет.
2. `ApplicationLoader.startPushService` запускает обычный `startService`,
   ошибки подавляются. `NotificationsService` не использует `startForeground`.
   Такой сервис не обеспечивает постоянную работу на современных Android.
3. `NotificationsSettingsActivity` записывает `pushService`/`pushConnection`
   в настройки текущего аккаунта; `ApplicationLoader` и `ConnectionsManager`
   читают глобальные настройки аккаунта 0. Для дополнительных аккаунтов
   переключатель службы может не менять фактическое поведение, а изменение
   соединения — не сохраняться после перезапуска. Это вывод из кода, настройки
   конкретного телефона из архива не извлечены.
4. Искусственная задержка в `scheduleNotificationDelay` равна 1 или 3 секундам
   (либо 0 с настройкой BYgram); она не объясняет длительные пропуски.

Ограничения жизненного цикла Firebase callback:
https://firebase.google.com/docs/cloud-messaging/android/receive-messages .
Ограничения фоновых служб Android:
https://developer.android.com/about/versions/oreo/background .

## Порядок исправления и проверки

Сначала восстановить регистрацию push: `account.registerDevice` должен
завершаться `BoolTrue` вместо `APP_PUSH_APIKEY_MISSING`. Затем проверить
реальное получение FCM при погашенном экране и закрытом интерфейсе и
исправить жизненный цикл обработки каждого push. Отдельно проверить настройки
для нескольких аккаунтов и поведение резервного соединения.

Новый APK, выкладка на сервер и изменение настроек внешних аккаунтов в рамках
диагностики не выполнялись. Секреты и содержимое сообщений из архива в отчёт
не перенесены. Без повторного теста после исправления нельзя обещать устранение
всех задержек на конкретном устройстве.

## Исправление ожидания push — 25.10.2026

По отдельному запросу исправлен Android `PushListenerController`: каждый вызов
`processRemoteMessage` создаёт собственный локальный `CountDownLatch`.
Этот же объект передаётся очереди уведомлений и в `onDecryptError`; окончание
одного push больше не освобождает ожидание другого. Сигнатуры публичного
обработчика и Firebase/Huawei-сервисов не менялись. Три ранних выхода при
некорректном `OAUTH_REQUEST` теперь освобождают ожидание своего push, чтобы
после перехода на локальный latch такие сообщения не блокировали обработчик.

`python Tools/check_bygram_push_completion.py` — PASS: последовательные FCM/HCM,
перекрывающиеся вызовы и изоляция завершения, ошибка расшифровки с пробуждением
аккаунтов. JVM-проверка исполняет извлечённые из production-кода постановку
в UI/stage-очереди, ожидание, передачу в очередь уведомлений и decrypt fallback;
разбор payload и Android API заменены заглушками. Три OAuth-выхода проверяются
контрактами исходного текста. Это не проверка доставки на устройстве.

Компиляция `:TMessagesProj:compileDebugJavaWithJavac` с
`-PBYGRAM_EDITION=full` завершилась успешно. Журнал:
`output/check-push-completion-java-2026-10-25.log`. Остались предупреждения
source/target Java 8 под JDK 21, deprecated API и unchecked operations.
Регрессионная проверка также отвергает прежнюю реализацию из HEAD с общим latch.

`APP_PUSH_APIKEY_MISSING` и настройки внешних аккаунтов этим изменением не
исправляются. APK не собирается по указанию пользователя.
