# Платные плагины в официальном каталоге BYgram

Технический план · 18 ноября 2026

[Реализация и запуск пилота](paid-catalog.md) описывают фактические маршруты, хранилище и тесты. Для TON принято прямое перечисление на подтверждённый кошелёк автора. Разделы плана про общий адрес BYgram описывают исходную схему.

## 1. Модель покупки и каналы оплаты

Покупатель один раз приобретает плагин по `plugin_id`. Право на загрузку и обновления привязано к подтверждённому Telegram-аккаунту. Покупка восстанавливается после переустановки приложения и на другом устройстве. В пилоте BYgram принимает платежи через своего бота и на свой TON-адрес, ведёт учёт долей авторов и проводит выплаты вручную. Подписки и автоматические выплаты вынесены за пределы пилота.

| Канал | Как принимать оплату |
| --- | --- |
| Telegram-бот, Mini App | Только Telegram Stars (`XTR`) для цифровых товаров. TON-кнопку и переход в TON-кассу из этих поверхностей не размещать. |
| Нативная standalone-сборка BYgram | Stars через штатную форму инвойса Telegram. TON отдельным сценарием через системный браузер и TON Connect после проверки правил канала распространения и применимых требований к приёму криптовалюты. |
| Самостоятельная веб-касса BYgram | TON Connect в обычном браузере. Право покупки попадает на тот же BYgram-аккаунт после подтверждения личности. |

BYgram распространяется как standalone-сборка. Внутри ботов и Mini Apps правила Telegram требуют Stars для цифровых товаров. Условия Telegram API для сторонних клиентов требуют раскрывать способы монетизации в описаниях приложения в используемых магазинах. [Telegram Stars Payments](https://core.telegram.org/bots/payments-stars), [Telegram API Terms](https://core.telegram.org/api/terms).

### Предупреждение перед оплатой

> После подтверждения оплаты и предоставления доступа к плагину возврат средств по желанию покупателя невозможен. Если платёж списан, а доступ не появился, или возникла другая проблема с оплатой, обратитесь в поддержку BYgram. Случаи обязательного возврата рассматриваются по применимым требованиям закона и правилам платёжной платформы.

Показывать предупреждение и ссылку на условия в BYgram, веб-кассе и боте до выдачи инвойса или запроса на перевод. Продолжать после явного согласия и сохранять в заказе версию условий и время подтверждения. Спорные платежи обрабатывает поддержка. Для Stars сохранить `/paysupport` и обработку возвратов, а для TON предусмотреть ручную корректировку, если подтверждённое исключение требует отдельного перевода. [Требования Telegram к условиям продажи и поддержке](https://core.telegram.org/bots/payments-stars).

## 3. Публикация, хранение и модерация

1. Расширить форму подачи заявки режимом «Платный», целочисленными ценами в Stars и наномонетах TON и описанием товара. Для пилота платный автор из списка допущенных аккаунтов загружает подписанный пакет через HTTPS с подтверждённой сессией. Бесплатный путь через GitHub продолжает работать. Закрытый GitHub с ограниченными правами приложения можно добавить при необходимости автоматизации. Платный архив, ранее опубликованный в открытом GitHub Release или статическом каталоге, считать уже распространённым.
2. Вынести проверку архива и подписи из ветки получения GitHub Release так, чтобы оба источника использовали одинаковые ограничения размера, ZIP, манифеста, версии и подписи. Хранить кандидаты и платные релизы вне webroot. Модератор видит описания, цены, возможности и изменения кода, скачивает именно проверяемый хеш и подтверждает его. Отдельно проверять работу с данными, сетевые обращения и хуки. Подпись удостоверяет происхождение пакета, а проверка его поведения остаётся частью ревью.
3. При первой публикации привязать `plugin_id` к подтверждённому автору и публичному ключу. Следующие релизы требуют той же привязки и большей версии. Передачу авторства и смену ключа провести отдельной административной операцией с журналом и повторным ревью. Цена и каналы продажи хранятся в предложении на сервере, SDK и схема подписанного манифеста остаются v1.
4. Сделать `catalog-v2` для нового клиента. Он объединяет бесплатные и платные карточки и публикует метаданные релиза, размер, SHA-256, ключ автора и доступные цены. В карточке платного релиза есть ID релиза и способ выдачи `entitled`; публичного URL пакета нет. Статический v1 по-прежнему содержит только бесплатные записи. Если v2 недоступен, клиент может показать бесплатный v1, сохранив платные покупки в отдельном представлении при наличии локальных метаданных.
5. Публиковать хешированный объект атомарно перед транзакционным переключением текущего релиза. При прерывании работы повторно применять ту же операцию. Фоновая сверка выявляет расхождения между хранилищем и БД. Снятие с продажи выключает новые заказы, но оставляет покупателям безопасные доступные версии. Отзыв конкретного небезопасного хеша останавливает выдачу и добавляет его в существующий список отзывов для клиента. Право покупки сохраняется для безопасной замены или денежного возврата.

## 4. Данные и серверный API

Использовать текущие PHP/PDO и MySQL/InnoDB. Миграции добавить рядом с `server/activity-api/migrations`, а свежую установку описать в `schema.sql`. Указанные имена маршрутов и таблиц проектные.

Текущая подпись Android-запроса рассчитана на POST. При реализации можно использовать POST actions существующего API, включая выдачу файла. При выборе GET подпись должна покрывать фактический метод и путь запроса. Сервер определяет платёжные методы по подтверждённому контексту начала checkout. Присланные клиентом канал и версия сами по себе не подтверждают происхождение сборки.

| Таблица | Основные поля и ограничения |
| --- | --- |
| `plugin_products`, `plugin_releases`, `plugin_offers` | Владелец, ключ, статус, текущий релиз. Уникальные `(plugin_id, version)` и SHA-256. Предложение содержит провайдер, валюту, целую сумму в минимальных единицах, канал, статус и ревизию цены. |
| `plugin_orders` | Случайный ID, Telegram ID покупателя, продукт, зафиксированные цена, автор и его доля, провайдер, канал, ревизия оффера, время истечения и статус. Idempotency key уникален для покупателя. Один активный checkout на покупателя и продукт, независимо от метода. |
| `plugin_payment_events`, `plugin_payments` | Inbox событий с уникальным ID источника. Записи платежей с уникальным ключом провайдера и сохранёнными суммами. Второй фактический платёж за один товар сохраняется для разбора и возврата. |
| `plugin_entitlements` | Уникальная пара `(telegram_id, plugin_id)`, источник выдачи, статус и дата изменения. При возврате пересчитать право с учётом других действительных источников. |
| `plugin_author_ledger`, `plugin_payouts` | Начисления, сторно и выплаты с отдельным учётом XTR и TON, ссылками на платёж, автора и расчётный период. |

- `GET /catalog-v2` возвращает публичные карточки. `POST /orders` принимает только продукт, метод и ключ повтора. Сервер вычисляет цену, проверяет совместимость и доступность метода для подтверждённого канала, фиксирует оффер. Смысл статусов заказа: `pending → paid → refunded`, `pending → expired/canceled`, спорные и запоздалые платежи поступают на разбор. Проверенная оплата после истечения срока сохраняется для обработки с учётом правил провайдера.
- `GET /orders/{id}` и `GET /entitlements` доступны владельцу. `GET /releases/{id}/download` проверяет подтверждённую сессию, владение продуктом и доступность именно этого релиза, затем стримит файл с `Cache-Control: private, no-store`. При локальном хранилище можно использовать внутреннюю отправку файла веб-сервером, если хостинг это поддерживает. Не передавать bearer-токен в URL. Ограничить частоту заказов, запросов состояния и загрузок.
- Применение подтверждённого платежа выполнять под блокировкой заказа и права покупки: записать платёж, сменить состояние, выдать entitlement, добавить проводку в одной транзакции. Маркер обработанного события фиксировать вместе с эффектами. Повтор того же события отвечает успешно без дополнительной выдачи. Два разных платежа обрабатываются как две финансовые записи с одним правом загрузки. Неподходящий платёж фиксируется для поддержки. Клиентские статусы оплаты только запускают обновление заказа.

## 5. Telegram Stars

1. Завести отдельного торгового бота, чтобы управление его токеном и webhook не влияло на авторизацию BYgram. Для заказа создать `createInvoiceLink` с валютой `XTR`, одним элементом цены, без внешнего провайдера и с непрозрачным `invoice_payload`, связанным с заказом. Ссылку открывать штатной формой для того же Android-аккаунта, который создал заказ.
2. Настроить отдельный HTTPS webhook через `setWebhook` с секретом в `X-Telegram-Bot-Api-Secret-Token` и типами событий `pre_checkout_query` и `message`. Проверить секрет, форму сообщения и допустимый размер тела. На `pre_checkout_query` ответить за 10 секунд после проверки Telegram ID плательщика, payload, суммы, валюты, состояния заказа и возможности исполнения. Под блокировкой закрепить принятую попытку за заказом и запоминать решение для повторной доставки того же запроса. При таймауте ответа сверять результат перед новой попыткой покупки.
3. Выдать доступ только по серверному `successful_payment` после повторной проверки Telegram ID, суммы, валюты и ссылки на заказ. Уникальный ключ платежа — `telegram_payment_charge_id`. Если `pre_checkout_query` уже был принят, задержка webhook сама по себе не отменяет покупку.
4. Поддержать `/paysupport`, `refundStarPayment`, события `refunded_payment` и регулярную сверку через `getStarTransactions`. Таймаут исходящего вызова сверять с историей до повторной финансовой операции. Отметка о возврате блокирует повторную выдачу при доставке событий в обратном порядке. На тестовом боте проверить всю цепочку до возврата. [Telegram Stars Payments](https://core.telegram.org/bots/payments-stars), [Bot API](https://core.telegram.org/bots/api#createinvoicelink), [Payments API для клиентов](https://core.telegram.org/api/payments).

## 6. TON

1. На standalone-клиенте создать заказ и открыть доверенный домен BYgram в системном браузере. Для перехода использовать короткоживущий одноразовый токен с отдельной областью действия, который обменяется на сессию кассы. При прямом входе с веба подтвердить тот же Telegram ID. Возврат в приложение содержит только ссылку на заказ, а клиент заново проверяет его через API.
2. На веб-кассе разместить TON Connect manifest. Сервер формирует запрос на один перевод нативной валюты сети: получатель BYgram, точная сумма в наномонетах, сеть, `validUntil`, непрозрачный уникальный идентификатор заказа в payload. Назначение и сумму показать до подтверждения. Приватные ключи покупателей остаются в кошельках. Приёмный адрес отделить от кошельков выплат, а ключ адреса держать вне PHP-хостинга.
3. Запустить отдельную CLI/cron-задачу сверки по API индексатора с сохранённым курсором и повторным чтением недавних записей. Webhook индексатора может ускорять обнаружение. Перед выдачей проверить сеть, фактическое успешное входящее сообщение на адрес продавца, сумму, payload, отсутствие bounce/abort и подтверждение в masterchain. Уникальный ключ привязать к сети и хешу входящего сообщения. Результат `sendTransaction`, BOC и хеш от клиента использовать только для поиска или индикации ожидания.
4. Для недоплаты, переплаты, повторного перевода, отсутствующего payload и позднего платежа завести очередь разбора. Движение TON необратимо после финальности. Возврат — отдельный исходящий перевод после проверки плательщика и реквизитов, с ручным подтверждением, своим идентификатором операции и сверкой сети перед сторно. Цена в TON фиксируется при создании заказа. Для пилота задать самостоятельную цену в каждой валюте. [TON Connect](https://docs.ton.org/applications/ton-connect/overview), [Обработка платежей и финальность TON](https://docs.ton.org/applications/payments/overview).

## 7. Интерфейс и границы лицензии

Для платного плагина штатная кнопка «Поделиться» отправляет ссылку на карточку товара. Пилот запускать с новыми ID платных продуктов, чтобы не менять условия доступа для ранее опубликованных бесплатных пакетов.

- В официальном каталоге показать цену и совместимость до оплаты. Состояния карточки: «Купить», «Ожидаем подтверждения», «Установить», «Обновить», «Снято с продажи». В «Моих покупках» показывать историю, установку на новом устройстве, повторную проверку заказа и вход в поддержку. При смене Telegram-аккаунта отменять незавершённую загрузку и игнорировать результаты старой сессии.
- Вести все платные каталожные загрузки через `PluginManager.stageCatalog`, подставив авторизованный транспорт перед имеющимися проверками пакета. Установку и обновление по-прежнему подтверждает пользователь. Покупка не включает исполнение Python-кода. Оплативший аккаунт получает право скачивания; глобальный плагин может действовать на устройстве шире этого аккаунта согласно его `account_scope`. Это условие показать до покупки.
- Пилот защищает выдачу файла с сервера. Любой скачанный пакет можно скопировать и попытаться установить вручную в модифицированном или совместимом клиенте. После возврата прекращаются загрузки и обновления по возвращённой покупке, локальная копия остаётся. Удалённое отключение по безопасности регулирует отзыв хеша. Если коммерческая модель потребует ограничения исполнения, проектировать его отдельно на уровне хоста с подписанными разрешениями, офлайн-сроком, проверкой при ручном импорте и правилами для глобальных плагинов. Для защищаемой функциональности поставлять чувствительную часть как серверную услугу.
- Авторы видят продажи, возвраты, резерв, ставку и доступный остаток. Долю и правила округления фиксировать при заказе. XTR-начисления и TON-начисления сверять раздельно. Если выплата автору идёт в TON из поступлений Stars, сохранять факт вывода, фактический курс, комиссию и проводки конвертации. До пилота согласовать продавца по документам, налоги и расчёты с авторами, резерв возвратов, допустимые страны и условия обработки персональных данных.

## 8. Порядок внедрения и критерии готовности

| Этап | Результат и проверка |
| --- | --- |
| 0. Подготовка | Утверждены условия продажи, обязательные исключения из политики возврата и правила выплаты. Проверены на staging PHP/cURL/ZIP/Sodium, InnoDB, HTTPS webhook, дисковое хранилище вне webroot, фоновые задачи, исходящие запросы и бэкапы. |
| 1. Каталог и права | Заявка с закрытым пакетом, ревью хеша, v2, миграция и защищённая загрузка. Тестовое право даёт загрузку только владельцу. Старый клиент читает v1. Платных байтов нет в публичном индексе, каталоге файлов и кэше. Проверены rollback публикации и повтор ревью. |
| 2. Stars и Android | Тестовый бот, форма оплаты, согласие с условиями, сверка и обработка исключительного возврата, Android-кнопки и восстановление. Прогнать отказ, отмену, смену аккаунта, повтор и нарушение порядка webhook, падение после commit, просрочку, двойную покупку и подмену суммы/пользователя. |
