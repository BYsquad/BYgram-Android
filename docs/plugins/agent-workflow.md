# Разработка плагинов BYgram с помощью ИИ

Рабочий процесс для написания, исправления, ревью, переноса и тестирования плагинов под BYgram Android. Пути в командах приведены от корня `BYgram-Android`. Для разработки вне репозитория используй инструкции по отдельному упаковщику в SDK и документацию версии, установленной у пользователя.

В установленном скилле каталог `references/` сохраняет структуру `docs/plugins/` и `Tools/`. Используй его как корень для путей к инструментам или вызывай вложенные скрипты по абсолютному пути. Исходники нового плагина и выходной пакет сохраняй в рабочем каталоге пользователя. В комплект входят упаковщик, конвертер и Dev Server. Проверки движка `check_plugins.py`, `check_extera_port.py` и `check_plugin_device.py` запускаются из полного репозитория BYgram. Проверки самого плагина, его манифеста и архива доступны и при автономной установке.

## Документация и примеры

- [Публичная документация BYgram](https://byxarek.site/TEST-PROJECT/BYgram/docs/) и [руководства на английском](https://byxarek.site/TEST-PROJECT/BYgram/docs/en/) описывают первый плагин, API и совместимость. [Репозиторий BYgram Android](https://github.com/BYsquad/BYgram-Android) содержит полный SDK и инструменты.
- [SDK v1](sdk-v1.md) задаёт публичный контракт. [Схема manifest v1](manifest-v1.schema.json) задаёт имена полей, типы и допустимые возможности. Для неоднозначностей сверяй документацию с реализацией в целевой ревизии. Внутренний метод клиента сам по себе не становится публичным API SDK.
- [Менеджер плагинов](README.md) описывает установку, разрешения, обновление и откат. [Dev Server](dev-server.md) описывает загрузку через ADB, live reload и отладку. [Проверки и выпуск](testing-and-release.md) описывают расширенную матрицу для движка и APK.
- [Перенос exteraGram и Elyx](exteragram-port.md) описывает поддерживаемые модули, зависимости и различия. Документацию exteraGram используй для выяснения поведения исходника, а доступность в BYgram проверяй по его слою совместимости.

## 1. Определи результат

Зафиксируй триггер или элемент интерфейса, ожидаемый эффект, затронутые данные и аккаунты, внешние действия и критерий приёмки. Если пользователь просит исправление, сначала воспроизведи исходную проблему в доступной среде и сохрани поведение существующего ID и настроек. Для ревью проверь исходники и манифест, опиши наблюдаемое последствие и укажи файл и строку.

Уточняй сборку BYgram или версию Telegram, когда выбор API или совместимость реально от них зависит. Если штатных точек расширения для запроса нет, сообщи, какая часть недоступна и что можно реализовать на подтверждённом API. Для нового плагина начинай с публичного `bygram.Plugin`. Для переноса существующего плагина сначала проверь совместимость его импортов, API, ресурсов и зависимостей.

## 2. Реализуй плагин и манифест

1. Возьми ближайший пример и его `manifest.json`. Создай каталог с `manifest.json`, Python-точкой входа и только необходимыми ресурсами. `entrypoint` вида `main.py:MyPlugin` должен соответствовать файлу и классу. Манифест SDK v1 указывает `"manifest_version": 1` и `"python": "3.11"`. Версия пакета имеет три числа. Сохраняй ID при обновлениях и указывай только подтверждённые диапазоны SDK и сборок.
2. Объяви минимальные `capabilities`. Для действия с аккаунтом проверь требования метода и используй `selected_accounts`, когда нужен grant. Исходи из аккаунта события, если действие связано с событием. Не подставляй произвольный активный аккаунт при пропавшей авторизации или отзыве grant. Для действий над сообщениями проверь поведение в защищённых и секретных чатах средствами SDK.
3. Регистрируй меню, события и другие вклады в `on_enable`. Привяжи собственные ресурсы и фоновые задачи к lifecycle, очищай их при выключении и выгрузке. Проверяй повторное включение и результаты, пришедшие после выключения. Код на уровне модуля и конструктор оставляй без внешних действий. Используй SDK для UI и фоновую очередь для медленных операций. Уточняй сценарии отправки и передачи данных, соблюдай заявленное поведение и не включай пользовательские данные или секреты в журналы и архив.
4. Для настроек используй документированные дескрипторы. При изменении формата сохранённых данных обнови `settings_schema`, реализуй миграцию и проверь старые данные. Сохраняй существующие ключи и типы, если задача их не меняет.
5. Для Telegram-перехватов и Java/ART используй соответствующий раздел SDK. Сначала проверь, достаточно ли обычного события, меню или SDK-действия. Для `hooks.raw` сверяй точную сигнатуру и перегрузку на целевой сборке, заполняй `hook_targets`, диапазоны `bygram` и `telegram` и `requires_hook_backend`. Проверяй срабатывание, удаление регистрации и поведение при недоступном backend. Вывод `art-targets` даёт сигнатуры, а совместимость подтверждается запуском и пробой на целевом Android.

## 3. Собери пакет

Для нативного плагина замени пути в команде на реальные. Положи выходной файл вне каталога исходников плагина.

```sh
python Tools/package_plugin.py path/to/my-plugin my-plugin.byplugin
```

Для переноса запусти конвертер. Здесь `--ui` приведён для плагина с меню чата или профиля. Выбери необходимые параметры по [таблице совместимости](exteragram-port.md). Для Elyx или EAF подставь исходный архив. Используй `--resolve-pypi`, если согласованная сборка требует скачать объявленные pure-Python wheels.

```sh
python Tools/port_extera_plugin.py path/to/my-plugin.plugin my-plugin.byplugin --ui
```

Упаковщик и конвертер не импортируют авторский Python. Передавай ключ подписи только в сценарии, где пользователь запросил подпись и предоставил доступ к ключу. Держи приватный PEM вне исходного каталога и пакета. Просмотри список файлов и манифест готового ZIP-архива. Сохрани напечатанный упаковщиком SHA-256 для передачи пользователю.

## 4. Проверь результат

### Локально

- Проверь синтаксис исходного Python для 3.11. Например, `python3.11 -m py_compile path/to/my-plugin/main.py` проверяет один файл. Для многофайлового плагина проверь все модули. Запускай эту команду интерпретатором 3.11. Байткод из `__pycache__` в пакет не включай.
- Сверь манифест с [JSON Schema](manifest-v1.schema.json), в том числе ID, версию, entrypoint, разрешения, область аккаунта и зависимости. Проверь, что ZIP читается, содержит нужные файлы и не содержит ключей, токенов или лишнего содержимого. Команда `python -m zipfile -t my-plugin.byplugin` проверяет целостность ZIP.
- Для нетривиальной логики плагина напиши небольшие тесты поведения. Изолируй чистые функции и подставь минимальный контекст SDK для callback, чтобы проверить нормальный сценарий, пограничные входы и ошибки. Проверь ожидаемые обращения к SDK, в том числе их отсутствие при запрещённом действии. При наличии тестов на `unittest` запуск из корня проекта плагина может выглядеть как `python -m unittest discover -s tests`.
- Если менялся движок, формат пакета или слой совместимости, запусти `python Tools/check_plugins.py` из корня репозитория. Нужны `java` и `javac` в PATH и Gson 2.11.0 в Gradle-кэше. Для переносов можно отдельно запустить `python Tools/check_extera_port.py`. Эти проверки покрывают штатные сценарии репозитория. Тесты конкретного плагина выполняй отдельно.

### В BYgram на Android

1. На тестовой установке открой **Настройки → Настройки BYgram → Плагины → Установить из файла**. Проверь карточку и заявленные возможности, подтверди установку, включи движок и плагин, а при необходимости выдай доступ тестовому аккаунту.
2. Выполни сценарий пользователя. Проверь выключение, повторное включение и перезапуск. Если менялись настройки, проверь сохранение и обновление со старой версии. Если есть аккаунты, проверь работу с разрешённым аккаунтом, отказ без разрешения и смену или выход из аккаунта. Повторяй внешние действия только на тестовых данных.
3. При отладке через [Dev Server](dev-server.md) выбери тестовое устройство через `adb devices`. Для уже запущенного сервера установи `BYGRAM_DEV_TOKEN` из диалога BYgram и используй `python Tools/plugin_dev.py --serial SERIAL attach`, затем `python Tools/plugin_dev.py --serial SERIAL deploy my-plugin.byplugin`. Для итераций есть `watch` и `reload`. Токен вводи через окружение и не выводи в отчёт.
4. При изменениях движка используй [расширенную матрицу](testing-and-release.md). Команда `python Tools/check_plugin_device.py SERIAL debug.apk --report output/plugin-device-report.json` устанавливает указанный APK и гоняет фиксированный Debug fixture на выделенном тестовом устройстве. Она не проверяет пользовательский пакет. `--expect-hooks` уместен, когда конфигурация должна поддерживать хуки.
5. Запиши версию BYgram, версию Android, тип сборки и результат. Если доступен только эмулятор, так и укажи. При отсутствии устройства пометь Android-проверку как «не запускалась» и предоставь шаги воспроизведения. Для ART зафиксируй точную целевую сборку и наличие проверки на физическом устройстве.

## 5. Передай результат

Приложи исходники и ссылку или путь к собранному `.byplugin`, если задача требовала пакет. Укажи ID, версию, SHA-256, установку, необходимые доступы, команды и результаты тестов. Отдельно назови ограничения и неподтверждённые версии. Если инструментов сборки нет, отдай полные файлы и воспроизводимые команды, а статус пакета укажи как «не собран». Локальная сборка плагина не требует сборки APK, доступа к серверу BYgram или публикации в каталог.

| Запрос | Ожидаемый результат |

| «Добавь в меню чата пункт, показывающий подсказку. Текст меняется в настройках» | Нативный пакет на базе `hello`, только `ui`, глобальная область, проверка выключения и настроек |
| «Покажи предпросмотр черновика в верхнем регистре и примени по подтверждению» | Ориентир на `composer`, работа с выбранным аккаунтом, сохранение текста при отмене, проверка отказа без grant |

| «Добавь хук, сигнатуру и целевую сборку я не знаю» | Агент запрашивает недостающие данные или проверяет их на устройстве, фиксирует статус совместимости и не подставляет выдуманную сигнатуру |
