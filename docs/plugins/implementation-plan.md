# Архитектура плагинов BYgram: исходный проект

Требования и варианты проектирования. Актуальное поведение описано в [руководстве](README.md) и [SDK](sdk-v1.md).

## 1. Результат и границы

Пользователь устанавливает собственный пакет с Python-кодом, видит его происхождение и возможности, отдельно разрешает исполнение, настраивает и отключает его на странице «Плагины». Автор меняет оформление, меню, экраны и поведение клиента через документированный SDK; для неподдерживаемых сценариев использует Java reflection и AliuHook.

Первая полноценная версия включает установку из файла, управление, SDK, хуки на проверенных устройствах, настройки, диагностику, safe mode, собственную документацию и примеры. Онлайн-магазин, учётные записи разработчиков, платные плагины, облачная синхронизация и runtime pip не требуются для этой версии.

Не обещаем буквальную возможность изменить всё: серверные ограничения Telegram, права Android, поведение вне процесса и произвольный native-код не управляются этим SDK. Новые классы Java/Dex, нативные модули и новые Android permissions нельзя незаметно добавить Python-файлом. Существующие ресурсы APK нельзя физически переписать в установленном подписанном APK; оформление меняется через runtime-провайдеры.

Сохраняйте изменения рабочего дерева, сделанные вне задачи.

## 3. Зависимости и обязательный технический прототип

### 3.1. Проверенные внешние факты

- [Chaquopy: версии](https://chaquo.com/chaquopy/doc/current/versions.html): 17.2 поддерживает AGP 7.3–9.4 и требует API 24; 16.1 поддерживает AGP до 8.13, но также требует API 24. 15.x допускает API 21, однако официальная матрица AGP заканчивается на 8.5.
- [Chaquopy: изменения](https://chaquo.com/chaquopy/doc/current/changelog.html): повышение minSdk произошло в 16.0; 17.x добавляет поддержку страниц памяти 16 KiB, при этом сторонние Android wheels требуют отдельных проверок.
- [Chaquopy: Gradle](https://chaquo.com/chaquopy/doc/current/android.html): плагин применяется в одном модуле на приложение; Python 3.11 сохраняет 32-битные ABI, 3.12+ — только 64-битные.
- Выбран [форк BYxarek/hook](https://github.com/BYxarek/hook), а не прежний upstream артефакт 1.1.3. Его README указывает поддержку LSPlant до Android 17 / API 37 и четыре ABI.
- [Конфигурация форка](https://github.com/BYxarek/hook/blob/28137a6287e78ec55aaaa439c3c8e4cae55c0cf0/core/build.gradle.kts): `com.aliucord:Aliuhook:1.1.4-api37.1`, NDK `30.0.16248370`, CMake `4.1.2`, minSdk 21; LSPlant собирается из исходников и статически включается в `libaliuhook.so`.
- [Chaquopy Python API](https://chaquo.com/chaquopy/doc/current/python.html): dynamic proxy реализует Java-интерфейсы; Java-класс нельзя просто унаследовать этим способом во время загрузки произвольного плагина.
- [Chaquopy: межъязыковые вызовы](https://chaquo.com/chaquopy/doc/current/cross.html): учитывать GIL и циклы ссылок Java↔Python.

### 3.2. Рекомендуемая исходная комбинация

Для прототипа: **Chaquopy 17.2.0 + Python 3.11 + все четыре текущих ABI**. Python 3.11 выбран ради 32 бит, а не как вечное ограничение SDK. Native pip-зависимости пока не добавлять. Проверить фактические Python patch-version и `.so` каждого ABI по артефактам.

Минимальная версия BYgram — **Android 7.0 / API 24**.

Python 3.11 и плагины используют API 24 и новее.

Зафиксировать форк AliuHook на **`28137a6287e78ec55aaaa439c3c8e4cae55c0cf0`**, версия **`1.1.4-api37.1`**, LSPlant **`6ac2280d8d88e14f0864c26ac97c1dc96713bde1`**. Не ждать merge [upstream PR #21](https://github.com/Aliucord/hook/pull/21): на момент проверки он открыт. `main`/`main-SNAPSHOT` не использовать как неизменяемую зависимость. Сохранить контрольные суммы AAR и транзитивных артефактов после своей воспроизводимой сборки.

API 36 и 37 входят в целевую поддержку выбранного backend; прежнее ограничение upstream README до API 35 больше не является основанием исключать их. Включение конкретных конфигураций в BYgram подтверждается интеграционной матрицей. На неподдерживаемой/непроверенной конфигурации backend не загружать: API-плагины работают без него, хуковые получают понятную причину. Native-падение `dlopen`/ART нельзя надёжно поймать Java-исключением.

### 3.2.1. Уже имеющиеся подтверждения и оставшаяся интеграция

По [отчёту автора PR #21](https://github.com/Aliucord/hook/pull/21): на x86_64 прошли 17 тестов на API 28, API 35 / 16 KiB и API 37 / 4 и 16 KiB. На API 21 — 16 PASS и один FAIL `shouldDisableProfileSaver`; этот API ниже принятого минимума BYgram. Это результаты библиотеки из внешнего отчёта, не повторный прогон в BYgram. [CI build на `6e866b0`](https://github.com/BYxarek/hook/actions/runs/41119632142) имеет статус Success; последующие коммиты меняли README.

Поэтому не исследуем заново, существует ли поддержка API 37. P0 проверяет совместную работу закреплённого форка с Python bridge, BYgram, R8 и его native libs. В опубликованном отчёте нет ARM runtime и отдельного API 36 прогона; эти проверки остаются в интеграционной матрице.

Сборка зависимости выполняется отдельно от Telegram: checkout закреплённого commit → init только `xz`, `lsplant` и необходимого `dex_builder` по README → NDK 30/CMake 4.1.2 → `:core:assembleRelease` / `:core:publishToMavenLocal`. Для локального прототипа допустим Maven Local; CI/выпуск используют контролируемый Maven repository с этим AAR, POM и hashes, а не произвольное содержимое `mavenLocal()`. Наличие координаты в исходниках не считать доказательством публикации в upstream Maven.

NDK Telegram 27.2 не повышать автоматически: готовый AAR строится своим toolchain. Проверить итоговый набор `.so`, зависимости Dobby/C++ runtime, отсутствие лишнего `liblsplant.so` и test DEX, совместимость 16 KiB после упаковки. Конфликт разных `libc++_shared.so` исследовать по артефактам; не скрывать его слепым `pickFirst`.

### 3.3. Прототип перед основным кодом

1. Зафиксировать build snapshot, JDK, AGP, Gradle, Python host, Chaquopy, AliuHook и транзитивные версии; не записывать секреты.
2. Проверить minSdk/manifest merge для BYgram во всех поддерживаемых app-модулях.
3. Запустить Python из Java и обратно; загрузить тестовый модуль из private storage.
4. Сделать Java-адаптер `XC_MethodHook`, передающий вызов в Python через интерфейс. Проверить before/after, изменение аргумента, результата, исключение оригинала, unhook.
5. Проверить вызовы private/overloaded/static методов и конструкторов, primitive/boxed/null типы. Abstract/native/boot-image методы не объявлять поддерживаемыми по аналогии.
6. Проверить release/R8 и поведение после JIT/AOT-прогрева. При inlining исследовать конкретные callers/deoptimization, не выключать оптимизации глобально.
7. Проверить ELF и ZIP alignment новых `.so`, затем реальный запуск в среде 16 KiB. Один zipalign не подтверждает совместимость ELF.
8. Измерить старт без плагинов, первый старт Python, память и размер зависимостей по ABI.
9. Проверить лицензионные требования Chaquopy, AliuHook, LSPlant, Dobby и совместимость их распространения с проектом; собрать notices. У Chaquopy MIT, у AliuHook OSL-3.0 по страницам репозиториев. Юридическая совместимость в этом плане не устанавливается.

Выход этапа: таблица интеграционных результатов для принятого API 24+, hashes зависимостей и подтверждение hooks/Python на API 36/37. Решение по API 23 уже принято; повторно его не запрашивать.

## 4. Архитектура

```text
Страницы «Плагины», «Плагин», «Настройки», «Журнал / восстановление»
                              |
                 PluginManager (единственный владелец состояний)
                  /           |              \
        PluginInstaller   PluginRegistry   PluginRuntime
        staging/commit    metadata/state   Chaquopy, один интерпретатор
                                               |
                                     Python SDK bygram.*
                                      /              \
                         стабильные host API     HookBridge
                         события/UI/настройки    Java XC_MethodHook → Python
                                      \              /
                              PluginScope: owned handles
```

Начать в существующем `TMessagesProj`, без отдельного Gradle-модуля движка. Применять Chaquopy только в этой библиотеке; не дублировать применение в app-модулях. Учитывать, что библиотеку используют Huawei, HockeyApp, Standalone и тестовое приложение: нельзя случайно добавить Python только в основной APK или сломать остальные конфигурации.

Пакет реализации: `org.telegram.messenger.plugins`. Разделение ответственностей:

| Компонент | Ответственность |
|---|---|
| `PluginManager` | Очередь операций, переходы состояний, включение/отключение, снимок UI |
| `PluginRegistry` | Атомарное локальное состояние и восстановление незавершённых операций |
| `PluginInstaller` | Чтение SAF URI, лимиты, manifest, staging, установка/обновление/удаление |
| `PluginRuntime` | Единственный запуск Python, import namespace, entrypoint, callbacks |
| `PluginScope` | Учёт подписок, хуков, заданий, меню, UI и освобождение ресурсов |
| `HookBridge` | Проверка сигнатур/типов, один dispatcher на Member, порядок и reentrancy |
| `PluginRecovery` | Доинициализационный safe mode, durable markers, карантин и rollback |
| Host API | Точки расширения в Telegram; добавлять по вертикальным сценариям, не все сразу |

Это логические роли: маленькие модели и helpers допустимо держать рядом, не создавать по файлу на каждый enum или метод.

Python SDK хранить в `TMessagesProj/src/main/python/bygram/`. Java-адаптер хуков компилируется в APK; импортируемому Python-плагину не нужен свой build-time static proxy для `XC_MethodHook`. Произвольные Java subclasses и генератор Dex не входят в v1. Свою страницу создавать через host API; Java listener-интерфейсы реализовывать dynamic proxy.

## 5. Обязательная страница «Плагины»

### 5.1. Навигация и внешний вид

В главной странице BYgram — отдельная строка **«Плагины»** непосредственно после «Кастомизация», подзаголовок «Включено N из M». Выделить именованный row ID, проверить уникальность, не менять существующие номера. Экран — `BygramPluginsActivity extends BygramSettingsPage`, в том же Java package, поскольку общий базовый класс сейчас package-private.

Использовать общий ActionBar, back, цвета `Theme`, `UItem`, `UniversalRecyclerView`, существующие диалоги и bulletins. Для состояния списка брать immutable snapshot менеджера; не запускать Python из binding/onDraw. Подписку страницы удалять при уничтожении fragment. После установки или возврата обновлять данные без пересоздания всей навигации.

`SettingsList` сейчас private внутри `BygramSettingsActivity`. На первом этапе новый экран может использовать `UniversalRecyclerView` напрямую; не копировать весь private-класс и не расширять его видимость без необходимости. Интеграцию `settingsPage`, `linkedRow`, `forLink` и маршрутов добавить осознанно: новый тип не должен получать null page и NPE при долгом нажатии.

### 5.2. Состав экрана

| Область | Содержимое и действие |
|---|---|
| Шапка | «Плагины», состояние движка; индикатор safe mode при необходимости |
| Главный переключатель | «Выполнять плагины», default off; включение не отменяет карантин отдельных пакетов |
| Действия | «Установить из файла», «Документация», «Диагностика и восстановление» |
| Фильтры/поиск | По имени/автору/ID; фильтры все/включённые/ошибки вводить, когда список это оправдывает |
| Список | Иконка, имя, версия, автор, описание, статус, переключатель |
| Пустое состояние | Понятное объяснение и установка; без фиктивного каталога |
| Несовместимость | Причина: SDK, приложение, Python, ОС/ABI, недоступные хуки |

Карточка плагина: ID, версия, автор, источник файла, SHA-256, состояние подписи, требуемые возможности, область аккаунтов, совместимость, дата установки/обновления, настройки, журнал, включение, удаление и при наличии «Откатить версию». Имя автора в manifest не считать подтверждением личности.

На ошибку переключателя — вернуть фактическое состояние и показать причину, не оставлять ложное «включён». Долгие операции — progress и disabled только для конфликтующих действий. Отмена выбора файла ничего не меняет. Отмена до commit удаляет только staging.

### 5.3. Обязательные сценарии

1. Установка: системный picker → копирование и валидация → карточка с предупреждением → «Установить выключенным»; отдельное «Включить» разрешает исполнение. До согласия ни import, ни eval, ни миграция кода не выполняются.
2. Включение: проверка совместимости/согласий → durable activation marker → load → enable → ACTIVE или FAILED с очисткой handles.
3. Выключение: сначала закрыть вход новым callbacks → дождаться допустимых текущих → disable/unload → cleanup → OFF. Если операции не завершились, показать необходимость перезапуска.
4. Удаление: отключить → удалить пакет; отдельно предложить удалить настройки. Данные Telegram не затрагивать.
5. Обновление: сравнение версий и возможностей, сохранение предыдущей версии и data snapshot, commit и применение после перезапуска.
6. Журнал: фильтр по плагину, копирование/экспорт по действию владельца, очистка; без автоматической отправки.
7. Восстановление: запуск без плагинов, «Отключить все», сброс данных выбранного плагина и откат его версии. Всё доступно без Python и AliuHook.

### 5.4. Локализация и доступность

Строки BYgram — en/ru/uk; plugin UI может иметь собственные словари с fallback en. Названия возможностей и предупреждение о доверенном коде переводит host, а не автор. Проверить TalkBack, focus, большие шрифты, длинные имена/RTL, day/night, edge-to-edge, поворот, планшет, открытие клавиатуры, уменьшенные анимации. Нельзя передавать безопасность установки на отрисовку плагина.

## 6. Модель расширения для широкой кастомизации

Стабильные host API использовать в первую очередь, raw hooks — дополнительный механизм. Не писать по отдельному хаотичному хуку на каждый плагин в исходниках Telegram. Для повторяемого сценария добавлять общую точку расширения с контрактом, а в core при выключенном движке — быстрый no-op.

| Область клиента | Поддерживаемое направление | Граница / особенности |
|---|---|---|
| Общая тема | Именованные цветовые overrides, drawables, радиусы и типографика в явно поддержанных местах | Не ломать contrast; scoped providers, не глобальная запись пользовательской темы |
| ActionBar и навигация | Действия, заголовок, дополнительные элементы | Уважать search/action mode, back и текущие glass/insets |
| Список чатов и папки | Декорации строк, подписи, меню, badges, локальный порядок отображения | Не менять серверные папки и unread storage скрыто |
| Экран чата | Меню сообщения, toolbar, панели, локальные визуальные преобразования | Исходное сообщение не мутировать для декоративного изменения |
| Сообщения/текст | Display-only formatter с корректными spans/entities | Копирование/ответ/доступность имеют явную семантику |
| Профиль/настройки | Именованные секции и строки, кнопки, собственные страницы | Не использовать числовые ID Telegram как plugin ID |
| Медиа/сторис | Меню, overlays, элементы управления и действия | Отдельный lifecycle; никаких Python callbacks на каждый кадр |
| Композер | Кнопки, команды, преобразование текста по явному контракту | Preview и отмена; не менять получателя незаметно |
| Уведомления | Локальное представление и действия | Android channels/permissions остаются системными |
| Запросы/ответы/updates | Сначала наблюдение и контролируемые трансформации с account context | Очереди Telegram, строгие типы TL, осторожность с повторными отправками |
| Звонки/камера/платежи | Сначала UI-расширения | Не обещать перехват native media, криптографии или платёжной логики |
| Внутренние Java-методы | Before/after/replacement через HookBridge | Экспериментально, зависит от build fingerprint, ОС, R8 и inlining |

Очередность покрытия: менеджер + собственные настройки → меню/тема/события страниц → список чатов/профиль → чат/композер → медиа/сторис → сетевые расширения. «Все экраны сразу» не является проверяемым этапом: для каждой поверхности нужны список поддерживаемых действий и собственные regression сценарии.

Для полной замены layout предложить host custom page и scoped UI factory; произвольная замена существующего View через raw Java остаётся авторской ответственностью и обычно требует перезапуска. Публичный API для отдельных system widgets Android не обещать.

## 7. Жизненный цикл и состояния

Разделить сохранённое желание владельца (`desiredEnabled`) и состояние процесса (`runtimeState`). В manifest нет права автоматически включать пакет. UI показывает оба: например, «Включён, требуется перезапуск».

```text
ABSENT → STAGED → INSTALLED_DISABLED
                    |
                LOADING → ACTIVE → STOPPING → INSTALLED_DISABLED
                    |        |
                  FAILED   QUARANTINED

INCOMPATIBLE / PENDING_RESTART — отдельные причины недоступности/отложенной операции.
```

Все install/update/enable/disable/delete сериализуются одной management-очередью. Состояние пакета и реестр меняются транзакционно; callbacks получают generation token. После отключения старое поколение не может регистрировать handles, писать данные через SDK или доставлять результаты заданий.

Порядок загрузки: metadata/compatibility → согласие по точному hash → namespaced import → создание plugin → `on_load` → `on_enable`. При ошибке любого шага — пометка FAILED и finally cleanup. Состав пакета доступен только после установки; top-level Python-код исполняется лишь при разрешённой загрузке.

При отключении: закрыть dispatcher → отменить queued work → дождаться in-flight callbacks без блокировки UI → `on_disable` → удалить handles в обратном порядке → `on_unload` → отпустить ссылки. SDK cleanup обязан работать даже при исключении в авторском cleanup. Нельзя гарантировать остановку произвольного авторского thread или возврат глобально изменённого Java-поля. В этом случае требуется restart.

Один интерпретатор Python на процесс, а не по интерпретатору на аккаунт/плагин. Модули плагина загружаются в namespace по ID, версии и generation. Не добавлять все корни в общий `sys.path`: это ведёт к коллизиям и подмене импортов. Relative imports и приватные pure-Python зависимости внутри собственного namespace; стандартные/host модули общие. Это предотвращение случайных конфликтов, не изоляция доверенного кода.

В v1 **без горячей замены обновлённого кода**: новая версия применяется при следующем холодном старте. Выключение отменяет host-managed действия сразу, а UI-чужие изменения могут требовать restart. Python runtime не пытаться разрушать и запускать заново в том же процессе.

## 8. Потоки, задержки, ошибки

- Main thread: создание/изменение View, навигация, краткие синхронные UI callbacks.
- Management queue: файловые операции, install/registry, организация lifecycle.
- Background work: ограниченная host-очередь для I/O/вычислений. Не обещать параллельный CPU Python из-за GIL.
- Hook callback исполняется на потоке оригинального Java-метода; его нельзя просто перенести в очередь и сохранить синхронную семантику.
- Сетевые/Telegram controller операции отправлять на требуемые очереди через host adapter. Не ждать main thread из background при удержании GIL/lock, если main уже ожидает Python.
- Для обычных событий — coalescing/backpressure, лимит очереди и учёт dropped events. Порядок сохранять в рамках account/event stream, не обещать общий порядок независимых очередей.

Начальные диагностические пороги: UI callback >4 ms — предупреждение; повторяющиеся >16 ms — пометка «замедляет интерфейс»; background lifecycle >2 s — предупреждение. Это бюджет дизайна, уточняемый измерениями, а не способ принудительного прерывания. Python/C/Java зависание нельзя безопасно остановить `Future.cancel` или произвольным timeout.

Не вызывать Python из `onDraw`, measure/layout горячих paths, декодирования каждого медиакадра. Для темы и decoration заранее рассчитывать Java-конфигурацию и применять её без Python в цикле отрисовки. Если автор намеренно хукает горячий путь, SDK показывает риск и статистику, но не гарантирует FPS.

Обычные Python exceptions перехватывать на границе SDK, записывать ID/version/callback/stack без содержимого сообщений. Первое исключение enable → FAILED; для runtime callbacks — начальный порог 3 ошибки за 60 секунд → quarantine. Порог и причина видны в журнале. Критические VM errors, native signals и повреждение процесса не маскировать как «плагин восстановлен».

## 9. Хуки и совместная работа расширений

Host владеет одним `XC_MethodHook` dispatcher на конкретный Java `Member`. Плагинам возвращается собственный handle. Это позволяет определить порядок и удалить один плагин без удаления остальных callbacks.

Идентификация цели: полное имя класса, имя метода либо constructor, точный список Java-типов аргументов, при необходимости ожидаемый return type. `null`, массивы, `int/long`, boxed типы, overloads валидируются до регистрации. Поиск по одному имени не является стабильным контрактом.

Порядок before: priority по убыванию, затем plugin ID, затем registration sequence. After — обратный для фактически вошедших before callbacks. Зафиксировать contract early-return и exception в SDK и тестах, не полагаться на случайный порядок загрузки AliuHook. Аргументы после before видны следующему; after видит текущее возвращаемое значение/исключение.

При исключении Python callback host восстанавливает собственный snapshot args/result/throwable до этого callback и продолжает цепочку; исходную ошибку Java не скрывать без явного `set_result`/`set_exception`. Snapshot не откатывает глубокую мутацию Java-объектов и внешние side effects — это явный предел гарантии. Проверка типа результата выполняется до передачи обратно Java.

Для replacement — один активный владелец на метод; второй получает конфликт с ID владельца. Другие наблюдающие хуки допустимы по определённому порядку. `call_original` — специальный обход hooks, максимум один вызов в обычном replacement contract; нельзя невольно вызвать оригинал дважды после исключения callback. После уже совершённых side effects автоматический повтор оригинала запрещён.

Reentrancy — ThreadLocal guard по plugin+member; повторный вход того же плагина пропускает его callback, сохраняя оговорённое выполнение остальных. Флаг очищается в finally. В документации привести рекурсивный пример и способы осознанного обхода.

Произвольное `disableHiddenApiRestrictions` или `disableProfileSaver` не включать глобально при старте. При необходимости — отдельное исследование конкретной проблемы. Не хукать нативные методы как обычные Java и не считать `XposedHelpers` частью AliuHook только из-за сходства API.

Для стабильных UI contributions использовать `(plugin_id, local_id)`. Для singleton overrides (например, глобального цвета) владелец выбирает приоритет, UI показывает победителя. Базовое значение сохраняется в настройках пользователя; отключение возвращает его через удаление override. Настройки BYgram не перезаписываются ради временного plugin effect.

Raw hooks требуют диапазона BYgram/Telegram build и перечня сигнатур. После обновления клиента такие пакеты переводить в проверку совместимости; точечный signature probe без исполнения кода. Совпадение имени метода не доказывает прежнюю семантику. Стабильные API-плагины продолжают работать в объявленном SDK диапазоне.

## 10. Пакет, хранение, установка и обновление

Формат v1 — ZIP с расширением `.byplugin`, `manifest.json`, `main.py` и optional assets/locales/vendor. Схема и пример — в [SDK](sdk-v1.md). Один формат проще проверять, документировать и обновлять. Импорт одиночных `.py`/`.plugin` exteraGram и автоматическое определение совместимости не входят в v1.

```text
files/plugins/
  registry.json
  recovery.json
  packages/<plugin-id>/<version>-<sha256>/...
  data/<plugin-id>/global/settings.json
  data/<plugin-id>/accounts/<stable-account-key>/settings.json
  staging/<operation-id>/...
  rollback/<plugin-id>/...       # предыдущий пакет и snapshot данных
cache/plugins/logs/...           # ограниченный диагностический журнал
```

Для registry/settings использовать существующие Android AtomicFile/JSON и отдельный private preferences recovery marker, а не новую SQLite/MySQL базу. Текущая серверная MySQL для локальной системы не нужна. В реестре: schemaVersion, install hash, source, fingerprint подписи, active/pending version, desiredEnabled, approved capabilities/hash, account policy и recovery status. Не хранить Telegram auth keys и пароли плагинов в manifest/registry.

Начальные ограничения: 10 MiB входной ZIP, 30 MiB распакованный пакет, 512 записей, 5 MiB один файл, manifest 64 KiB, глубина пути 12. Это лимиты v1 с понятной ошибкой; пересмотреть только по реальным примерам. Реальный streaming byte counter обязателен: заголовки ZIP недостоверны. Лимиты путей, количества и суммарного размера независимы.

Отклонять traversal (`..`, абсолютные пути, drive prefix, backslash-обходы), symlink, duplicate entries/normalized paths, encrypted ZIP, неподдержанные записи и несовпадающие hash. Canonical target каждого файла обязан оставаться в staging. Не исполнять `.pyc`, `.dex`, `.jar`, `.so` из пакета v1; проверка не делает остальные `.py` безопасными. Не следовать сетевым ссылкам из manifest при установке.

Установку через SAF вести streaming в private staging: validate schema → список/размеры → распаковка с ограничениями → hashes → compatibility → карточка согласия → atomic rename на том же volume → атомарная запись registry. `entrypoint` разрешать только как относительный путь к `.py` плюс имя класса по строгой грамматике. Из manifest не выполнять Python и не импортировать класс для чтения метаданных.

Одинаковый ID без смены версии/содержимого — «уже установлен»; тот же version с другим hash — отдельная явная замена, без автоматического доверия. Downgrade — только по действию владельца. ID и автор не являются механизмом доверия; новый файл с существующим ID не должен автоматически наследовать разрешение исполнения. Для неподписанных обновлений явно повторять подтверждение; для подписанных проверять тот же ключ, а смену ключа — отдельным действием.

В v1 подпись не обязательна для собственных локальных пакетов: показывать «Подпись не проверена». SHA-256 доказывает только целостность/идентичность выбранного файла. Проверяемые publisher-подписи и доверенные ключи добавить вместе с каталогом; не изображать значок «безопасный» на основании одного hash или самоподписанного manifest.

Update: stage новой версии → validate → показать изменения возможностей/ключа → сохранить старый пакет/data snapshot → выставить pending → при следующем старте durable migration marker → миграция settings → enable → commit успешного activation. Ошибка/падение в незавершённой активации → восстановить snapshot, оставить новую версию выключенной, предложить старую. Не запускать две версии одного ID одновременно.

Registry содержит operation journal или эквивалентные pending поля: после process death проверить соответствие файлов/версий и завершить либо откатить транзакцию. Потеря питания/нехватка места между rename и registry write не должна уничтожать последнюю рабочую версию. Миграцию settings выполнять только после согласия на исполнение; external side effects авторской миграции откату не поддаются.

## 11. Аккаунты, область данных и экспорт

Код и факт установки глобальны для приложения. UI/theme plugins могут действовать глобально; message/network callbacks обязательно получают `account` и выполняются только в выбранных владельцем аккаунтах. Не брать `UserConfig.selectedAccount` в отложенном callback: выбранный аккаунт мог измениться.

Ключ account data связан с Telegram user ID и поколением авторизации, а не только с числовым slot. На logout: закрыть callbacks, отменить account jobs, удалить или по явному правилу очистить account data, не отдавать его новому пользователю в том же slot. Фоновый результат с прежним generation отклонить. Плагин не включается автоматически для вновь добавленного аккаунта.

Выбор аккаунтов ограничивает поддерживаемые SDK вызовы; raw Python/Java в том же процессе может обойти эту политику. Это нужно объяснить в UI доверия. Скрытые/защищённые чаты не передавать стабильному API до штатной разблокировки. API не должен предлагать обход PIN; честно указать, что злонамеренный in-process код нельзя технически удержать тем же SDK.

Host settings — отдельные global/account stores с версией схемы и JSON-типами. Пример лимита SDK data — 1 MiB settings на scope; не включать media cache. Миграции атомарны, с backup. Не хранить Activity/View/account client в глобальном Python singleton без lifecycle очистки.

Экспорт настроек BYgram в v1 **не экспортирует код плагинов и согласие на исполнение**. Отдельный экспорт plugin settings — только по действию пользователя, с предупреждением о возможных пользовательских данных. Импорт данных допустим для установленного ID, проходит schema migration после согласия и не включает пакет. Сброс BYgram не должен незаметно удалять плагины: отдельный «Сбросить плагины» со списком последствий. Android backup правила исключают исполняемые пакеты/согласия и recovery markers; после восстановления код не запускается автоматически.

## 12. Доверие и реальная безопасность

Python имеет Java bridge и работает с UID BYgram. Импортные ограничения, список capabilities и отдельные директории **не являются sandbox**. Даже плагин «только тема» потенциально способен обратиться к сети, файлам и аккаунтам напрямую. Это ограничение относится ко всему исполняемому Python, а не только к кнопке «Расширенные хуки».

Первое включение движка и каждого нового/изменённого исполняемого пакета показывает host-предупреждение: «Плагин выполняет код внутри BYgram и потенциально может читать данные аккаунтов, отправлять сообщения и обращаться к сети. Включайте только код, которому доверяете». Декларации `ui`, `messages.observe`, `messages.send`, `network`, `hooks.raw` описывают ожидаемое использование и контролируются SDK; они не гарантируют отсутствие других действий.

В v1 нет тихой установки из сообщения/deep link, автоисполнения вложения, runtime pip, shell installer, удалённого eval или автозапуска dev server в release. Файлы открываются системным picker; интеграция «установить из Telegram» позднее всё равно проходит host-карточку и отдельное согласие.

Внутренние API плагинов не дают токены BYgram backend и не обходят лицензирование. Сервер по-прежнему самостоятельно проверяет полномочия: локальная проверка всегда может быть изменена кодом плагина. Обновлять production и подключаться к FTP для локального runtime не требуется.

Журналы host: plugin ID/version, stage, error code и sanitized stack. Не писать текст сообщений, телефоны, auth keys, content URI, сетевые headers и payload по умолчанию. Авторский `print`/logger может сам вывести чувствительные данные; не обещать абсолютную очистку и никогда не отправлять журнал без владельца. Лимит: например, 1 MiB на плагин и 10 MiB всего, ring rotation.

Если в будущем нужны **недоверенные безопасные расширения**, проектировать отдельный режим декларативных тем/правил без Python либо отдельный Android isolated process с IPC и узким API. Вызов Java-методов и UI из того процесса напрямую невозможен; это другой уровень полномочий, а не галочка текущего движка. Обычный `android:process` с тем же UID сам по себе не создаёт нужную изоляцию.

## 13. Восстановление и предотвращение boot loop

Recovery читается до старта Chaquopy и загрузки AliuHook. Записывать durable marker до каждого import/enable/update migration и очищать после успешного шага. Незавершённая активация при следующем старте — подозрение, не доказательство вины плагина: process death может быть системным. По умолчанию открыть клиент в safe mode и предложить восстановление; данные аккаунтов не удалять.

При обычном runtime exception виновник известен по PluginScope — quarantine только его. При native crash, ANR или неоднозначном падении — safe mode для всех, показать последнюю активируемую версию и последние host stage markers без утверждения о точной причине. В `onTerminate` не полагаться: Android не гарантирует этот callback.

Ведение startup-session marker и подтверждение здорового старта после устойчивой работы главного экрана; серия незавершённых стартов (начально 2) включает safe mode. Force-stop/обновление/перезагрузка могут дать ложное подозрение — recovery должен быть обратимым и понятным. Нельзя надёжно классифицировать все завершения процесса только marker-файлом.

С 12.11.2026 BYgram автоматически включает безопасный режим в фоновой очереди при запуске после прерванной активации или при ошибке восстановления. Приложение открывается без плагинов и показывает уведомление, если Android разрешает уведомления BYgram. Нажатие открывает экран в отдельном процессе `:plugin_recovery`; он также доступен из настроек плагинов. Выход из безопасного режима оставляет движок и плагины выключенными.

Recovery пишет только отдельный atomic recovery preferences/flag, а не одновременно registry основного процесса; основной процесс перечитывает его на resume/start. Если основной завис, изменения гарантированно действуют при следующем холодном старте; инструкция предлагает штатно закрыть/перезапустить приложение. Проверить сценарий, когда main-process Python завис до первого кадра. UI recovery не импортирует plugin icons/layouts и не выполняет авторский cleanup.

Откат пакета/settings не откатывает уже отправленные сообщения, запросы, изменённые файлы вне PluginStore или другие side effects. Это явно показывать в документации.

| `Tools/`, `TMessagesProj_AppTests` | Реальные проверки формата, lifecycle, hooks и recovery |
| `docs/plugins`, `docs/bygram-settings`, `docs/build.md`, `changelog.md` | Обновлять по фактически реализованному этапу |

Не делать `-keep class org.telegram.** { *; }` как универсальное решение. Текущие широкие messenger rules уже есть, но UI reflection и inlining всё равно требуют точечных правил/проверок. Результаты R8 и размер APK фиксировать сравнением.


## 15. Этапы, зависимости и критерии завершения

| Этап | Работа | Измеримый результат / условие перехода |
|---|---|---|
| P0 — совместимость | Прототип с BYxarek/hook из раздела 3, minSdk/ABI/licences, benchmark baseline | Применено принятое API 24+; проверена интеграция API 24/35/36/37 и 16 KiB, закреплены hashes |
| P1 — менеджер без исполнения | Native страницы, schema/installer/registry, установка выключенным, удаление | Любой файл проверяется без запуска кода; process-death/плохой ZIP не теряют предыдущий пакет |
| P2 — runtime + SDK ядро | Lazy Python, lifecycle, scope, global/account settings, queue/logging | Hello-plugin включается/выключается, не оставляет callbacks, ошибка изолируется на границе SDK |
| P3 — восстановление | Markers, safe mode, recovery Activity/process, quarantine | После тестового зависания/падения клиент открывается без плагинов; настройки Telegram целы |
| P4 — stable UI API | Собственные страницы, настройки, menu contributions, theme overrides, события | Три эталонных UI-плагина работают без AliuHook и после удаления возвращают обычный UI |
| P5 — raw hooks | Java dispatcher/bridge, типы, ordering, conflicts, reentrancy, release | Пройдены before/after/replace/unhook и два конфликтующих плагина в проверенной матрице |
| P6 — расширение покрытия | Чат/профиль/диалоги/композер, затем наблюдение network | У каждого нового API контракт, пример, минимум один содержательный regression test |
| P7 — обновления | Pending version, settings migration, backups, rollback, logout/relogin | Прерывание update на каждом шаге приводит к старой или новой целой версии, не смеси |
| P8 — выпуск v1 | SDK stubs/docs/examples, release/R8/native checks, accessibility, финальный APK | Выполнен [чек-лист](testing-and-release.md), один итоговый APK доставлен в Избранное |

P3 обязателен **до выдачи исполняющего движка пользователям**. Внутренние проверки P2 допустимы только с контролируемыми тестовыми пакетами. P5 зависит от P0 и P3. P7 проектируется с P1, чтобы не переделывать формат хранения. По окончании каждого пункта обновлять changelog и docs, не только в конце всей разработки.

Оценка для одного разработчика после P0: P1–P4 примерно 12–20 рабочих дней; P5–P7 ещё 12–20; P8 5–10. Это предварительный диапазон **29–50 рабочих дней**, без каталога и без гарантии покрытия всех внутренних классов Telegram. Сам P0 — ориентировочно 3–5 дней; проблемы интеграции ART/16 KiB требуют переоценки. Не выдавать оценку за срок обязательства.

## 16. Собственная документация и совместимость с exteraGram

[exteraGram docs](https://plugins.exteragram.app/docs) полезны как пример структуры: lifecycle, settings, logging, Java bridge, high-level client helpers. Его текущая страница introduction и отдельная multi-account документация указывают разные минимальные SDK baseline; готовность конкретного API проверяется по его странице, а не по одному overview.

Заимствовать понятный автору подход, но публичный namespace сделать `bygram.*`; версии SDK — собственные. Не заявлять совместимость со всеми `.plugin`/Elyx-пакетами. AliuHook + Chaquopy сами по себе не предоставляют `base_plugin`, `client_utils` и другие модули exteraGram.

После v1 возможно исследование optional compatibility adapter для ограниченного набора API exteraGram. Сначала inventory реальных плагинов и тесты; неизвестный import должен давать ясную ошибку, а не запускать частично совместимый код. Копирование исходников/документации проверять отдельно по лицензии.

Публичная документация должна включать: установку и доверие; quickstart; manifest; lifecycle; account/thread model; UI settings; theme/menu/page API; hooks и reflection; storage/migrations; обновление и recovery; производительность; ошибки; совместимость версий; cookbook; reference и changelog SDK. В этом каталоге уже есть исходная спецификация и test/release plan.

При реализации добавить `.pyi`/type hints для IDE, JSON Schema manifest, несколько коротких **исполняемых** примеров и команды их упаковки. Сейчас примеры являются проектом API. Один простой packaging/check script без сторонних зависимостей достаточен; отдельный CLI framework не нужен. SDK reference и stubs проверять на соответствие реализации.

Сайт документации — следующий способ публикации этих Markdown, не необходимая зависимость runtime. Адрес не придумывать и не встраивать в UI до реальной публикации; для v1 использовать существующий repository/docs URL либо bundled help. Не поднимать production API/MySQL для локальной установки.

## 17. Принятые решения и оставшиеся предложения

| Вопрос | Решение / статус |
|---|---|
| Минимальный Android | Android 7.0 / API 24 |
| Runtime | Chaquopy 17.2.0, Python 3.11, четыре ABI — кандидаты P0 |
| Hook backend | Выбран BYxarek/hook `28137a6287e78ec55aaaa439c3c8e4cae55c0cf0`, `1.1.4-api37.1`; поддержка до API 37, интеграция BYgram — P0 |
| Android 16/17 | В целевой матрице API 36/37; учитывать имеющиеся тесты форка, проверить связку с BYgram |
| Формат | `.byplugin` ZIP + JSON manifest, локальная установка выключенным |
| Разрешения | Декларации SDK + честное доверие всему коду; sandbox не обещать |
| Обновления | По действию владельца, новая версия после restart, одна rollback версия |
| Hot reload/pip/catalog | Не включать в v1; появятся только при самостоятельной потребности |
| exteraGram compatibility | Ориентир UX/SDK, не бинарная/исходная совместимость v1 |
| Сервер | Не нужен для v1; документация и пакеты могут храниться в репозитории |

Следующее конкретное действие реализации — P0. До его результатов допустимо разрабатывать native менеджер/формат, но нельзя объявлять совместимость готовой.
